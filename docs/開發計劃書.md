# WS 牌組管理器 — 開發計劃書

**版本** v1.8 — 卡表線上更新改為分作品版本號並完成實作
**日期** 2026-08-04
**目標平台** iOS 17+（iPhone 為主，iPad 相容），Xcode + SwiftUI
**用途** 個人使用，不上架

---

## 1. 專案目標與範圍

### 1.1 要做的事

建立一個 iOS 原生應用程式，讓使用者可以：

1. **搜尋卡片** — 依卡號、卡名、等級、顏色、費用、特徵、觸發圖標、能力文字關鍵字進行篩選
2. **管理牌組** — 建立多個牌組，自由新增/刪除卡片並調整張數；可指定同一張卡各稀有度分別放幾張
3. **檢視卡圖** — 顯示官方卡片圖片；首次瀏覽時線上下載，之後永久快取於本機。可自行決定是否使用行動數據
4. **閱讀中文卡面** — 所有卡片的名稱與能力文字都有預先翻譯好的繁體中文，完全離線
5. **規則檢查** — 即時顯示牌組是否符合 WS 建構規則（50 張、CX 8 張、同名 4 張）
6. **統計檢視** — 等級曲線、顏色分布、觸發圖標分布
7. **卡表線上更新** — 新彈或翻譯修正時，App 內偵測新版並一鍵更新卡片資料，不必重裝 App
8. **牌組圖片分享** — 把牌組畫成一張圖，圖上帶 QR；對方存下這張圖就能掃回整副牌組（見 §4.4.9）
9. **依作品瀏覽** — 圖鑑先選作品再看卡，搜尋仍在最上面可直接跳過這一層（見 §4.3）

### 1.2 不做的事（明確排除）

- 不做對戰模擬 / 線上對戰
- 不做雲端同步、不做帳號系統
- 不上架 App Store（僅安裝於自己的裝置）
- 不做 App 程式本身的自動更新（iOS 禁止；介面已定案，程式改版另循 Xcode 重裝）
- iPad 佈局不特別優化（可執行，但先以 iPhone 為主）

> **v1.7 更正**：「不做多作品支援」已經作廢。`meta.title_code` 本來就預留了，實際擴充成本也確實不高，
> 目前收錄 10 部作品共 3,427 張卡（BD/W54、HOL、BD/W125、UMA、OVL、SFN、NIK、BRD/W139、CSM、BTR）。
> 卡片數大一個量級之後，原本「一次攤開全部卡片」的圖鑑就不合用了，這是 §4.3 改成兩層的直接原因。

### 1.3 資料規模預估

| 項目 | 數量 |
|---|---|
| 補充包普通卡 | 約 100 種 |
| 預組（TD）卡 | 約 17~20 種 |
| 平行卡（SR/SP/SSP 等） | 約 100+ 種，**能力文字與普卡相同，不重複翻譯** |
| **實際需翻譯的唯一卡片** | **約 120 種** |
| 預估 JSON 檔案大小 | 300~500 KB |
| 卡圖數量（含平行卡） | 約 220~250 張 |
| 卡圖快取容量（單張 80~150 KB） | 約 20~35 MB |

> **關鍵設計決策**：平行卡（例如 `BRD/W139-075S`、`BRD/W139-075SSP`）與普卡 `BRD/W139-075` 的**卡名與能力文字完全一致，但圖片與稀有度不同**。
>
> 因此採「一卡多刷」結構：翻譯以邏輯卡片為單位只做一次，但每個刷版各自保有卡號、稀有度與圖片網址。**牌組內可指定某張卡各刷版分別放幾張**（例如泰蕾莎 4 張 = 2 RR + 1 SR + 1 SSP），滿足收牌與實體牌組對照的需求。

## 2. 系統架構總覽

本專案分為**兩個完全獨立**的部分，執行順序不可顛倒：

```
┌─────────────────────────────────────────────┐
│  階段一：資料建置管線（Python，一次性）        │
│                                             │
│  ws-tcg 官網                                │
│      ↓ 抓取                                  │
│  raw_cards.json（原始日文）                  │
│      ↓ 術語表正規取代                         │
│  半翻譯狀態                                  │
│      ↓ Claude API 批次翻譯                   │
│      ↓ 自動化驗證 + 人工校對                  │
│  brd_cards.json（最終產物）                  │
└──────────────────┬──────────────────────────┘
                   │ 手動拖入 Xcode
                   ↓
┌─────────────────────────────────────────────┐
│  階段二：iOS App（SwiftUI）                  │
│                                             │
│  brd_cards.json（Bundle 唯讀資源）           │
│      ↓ 啟動時載入至記憶體                     │
│  CardDatabase（唯讀，可搜尋）                 │
│                                             │
│  SwiftData（可寫）                           │
│      └ Deck / DeckEntry（使用者牌組）        │
└─────────────────────────────────────────────┘
```

**這樣切分的理由**：卡片資料是靜態的（一彈發售後不會再變動），沒有理由讓 App 承擔爬蟲與 API 呼叫的複雜度。App 端只需要讀一個 JSON，程式碼會乾淨非常多，也不需要處理網路錯誤、API 金鑰管理、翻譯延遲等問題。

## 3. 階段一：資料建置管線（Python）

### 3.1 資料來源

**主要來源**：Weiß Schwarz 官方卡表 `https://ws-tcg.com/cardlist/`

**⚠️ 待驗證項目**：官網的卡表查詢介面近年改版過，實際的請求方式（GET query string 或 POST form、參數名稱、是否有分頁）需要在開工第一步用瀏覽器開發者工具實際確認。**這是整個專案風險最高的一點，應該最先驗證**。

備援方案（若官網難以自動化抓取）：
- 手動從官網分頁複製貼上（120 張的量，花 1~2 小時可以人工完成，並非不可接受）
- 參考卡查網站（需確認其使用條款是否允許）

**需要抓取的欄位**：

| 欄位 | 日文原名 | 範例 |
|---|---|---|
| 卡號 | カード番号 | BRD/W139-075 |
| 稀有度 | レアリティ | RR |
| 卡名 | カード名 | ビーチの天使 テレーゼ |
| 卡片種類 | カード種類 | キャラ / イベント / クライマックス |
| 顏色 | 色 | 黄 / 緑 / 赤 / 青 |
| 等級 | レベル | 0 |
| 費用 | コスト | 0 |
| 力量 | パワー | 3000 |
| 魂傷 | ソウル | 1 |
| 觸發圖標 | トリガー | 門 / 寶 / 扉 / 無 |
| 特徴 | 特徴 | 《魔法》《海》 |
| 能力文字 | テキスト | 【自】このカードが手札から… |

**爬蟲禮儀**：每次請求間隔 1~2 秒，設定 User-Agent，總請求數約 120~200 次。這是個人一次性使用，量很小。

### 3.2 資料模型（JSON Schema）

```json
{
  "meta": {
    "title_code": "BRD/W139",
    "title_name_jp": "ブラウンダスト2",
    "title_name_zh": "棕色塵埃2",
    "generated_at": "2026-07-22T10:00:00+08:00",
    "schema_version": 1,
    "card_count": 120
  },
  "cards": [
    {
      "id": "BRD/W139-075",
      "printings": [
        { "id": "BRD/W139-075",    "rarity": "RR",  "image_url": "https://...", "is_foil": false },
        { "id": "BRD/W139-075S",   "rarity": "SR",  "image_url": "https://...", "is_foil": true  },
        { "id": "BRD/W139-075SSP", "rarity": "SSP", "image_url": "https://...", "is_foil": true  }
      ],
      "name_jp": "ビーチの天使 テレーゼ",
      "name_zh": "海灘天使 泰蕾莎",
      "card_type": "character",
      "color": "yellow",
      "level": 0,
      "cost": 0,
      "power": 3000,
      "soul": 1,
      "trigger": "soul",
      "traits_jp": ["魔法", "海"],
      "traits_zh": ["魔法", "海"],
      "text_jp": "【自】 このカードが手札から舞台に置かれた時、…",
      "text_zh": "【自】 這張卡從手牌置於場上時，…",
      "text_lines_jp": ["【自】 …", "【永】 …"],
      "text_lines_zh": ["【自】 …", "【永】 …"],
      "translation_status": "reviewed",
      "source": "booster"
    }
  ]
}
```

**欄位設計說明**：

- `id` 為基礎卡號；`printings` 陣列列出所有刷版（普卡也在其中，固定放第一個），搜尋時任一刷版卡號都能命中
- `image_url` 只存網址不存圖片本身，JSON 維持輕量；圖片由 App 端按需下載並快取（見 §4.4.6）
- **⚠️ 待驗證**：官網卡圖的網址規則需要在 M0 一併確認。若能從卡號直接推導出網址（例如固定前綴 + 卡號轉換），就不必逐張抓取；若不行則需從卡表頁面的 `<img>` 標籤解析
- `text_lines_*` 把能力按行拆開，方便 App 端逐條顯示與翻譯品質檢查
- `translation_status` 三種值：`machine`（僅機器翻譯）/ `reviewed`（已人工校對）/ `manual`（人工重寫）。App 端可以對未校對的卡片顯示提示
- `source` 值為 `booster` 或 `trial_deck`，方便你判斷哪些卡要靠買預組取得
- 事件卡與 CX 卡的 `power` / `soul` 為 `null`

### 3.3 翻譯策略（三層）

WS 的卡面文字是高度模板化的，這是本專案最有利的一點。翻譯採三層漸進處理：

#### 第一層：術語表正規取代（確定性，100% 準確）

先用固定對照表把所有遊戲術語替換掉。這一層完全不需要 AI，且結果穩定可預期。詳見 §3.4。

#### 第二層：LLM 批次翻譯（處理剩餘句構）

經過第一層之後，剩下的多半是連接句構（「〜した時」「〜してよい」「〜を選び」）。這些交給 Claude API 處理。

**Prompt 設計要點**：

1. 把完整術語表當作 glossary 塞進 system prompt，強制使用既定譯名
2. **明確要求：所有數字、卡號、`【】` 標記、`《》` 特徵符號、`「」` 卡名一律原樣保留**
3. 一次送 10~20 張卡，要求回傳 JSON 陣列，降低 API 呼叫次數
4. 溫度設 0，追求穩定而非創意
5. 提供下方 few-shot 範例，示範理想的翻譯風格

**排版與符號規則**（從實卡範例歸納，寫入 prompt 硬性要求）：

| 規則 | 說明 | 範例 |
|---|---|---|
| 能力標記保留方括號 | 【自】【永】【起】【手】【對】原樣 | `【自】此卡從手牌…` |
| 成本框用方括號 | 費用/代價用 `〔 〕` 包住 | `〔(1) 手牌1張放到休息室〕` |
| 關鍵字方括號保留 | 【CX連動】【橫置】【反擊】等 | `【CX連動】〔(1)〕` |
| 卡名用「」 | 場上具名卡、CX 名 | `「OVER ZONE」` |
| 巢狀能力用『』 | 連動/賦予的下層能力整段包起 | `…獲得以下能力。『【自】此卡攻擊時…』` |
| 被動語態保留 | 「置かれた時」譯「被放置到…時」 | 不簡化成「放到…時」 |
| 主詞統一 | あなた→你、相手→對手 | 全篇一致 |

**few-shot 範例來源**：使用者提供的 7 張 NIK/S117（勝利女神 NIKKE）實卡譯文作為語感基準，涵蓋 Lv0 檢索、CX 連動、應援、集中、助太刀、經驗條件、賦予能力等主要句型。這些僅作為**風格與排版的示範**，實際 BRD 卡片仍由本管線重新翻譯，不直接引用其文字。

#### 第三層：自動化驗證 + 人工校對

**自動化檢查**（腳本執行，不通過就標記出來）：

- 數字集合比對：`re.findall(r'\d+', text_jp)` 與 `text_zh` 的結果必須完全一致 → 防止 LLM 把 3000 寫成 3500
- `【】` 標記數量與內容必須一致
- `《》` 特徵數量必須一致
- 譯文中不應殘留任何日文假名（平假名/片假名），有殘留代表漏翻
- **術語一致性**：若原文含 `控え室`／`山札`／`ストック`／`クロック`，譯文必須分別出現 `休息室`／`牌組`／`能量區`／`傷害區`，且不得出現舊譯（待機區、牌庫、資源區、時鐘區）→ 防止 LLM 繞過第一層自行改字
- 譯文長度不應少於原文的 40% 或超過 250%

**參考範例（語感基準，節錄自使用者提供的 NIK/S117 卡片）**：

```
【永】應援 在你的回合中，此卡前面的你的角色全部，攻擊力+X。X等於那張角色的等級×1000。
【起】〔(2) 手牌的CX1張放到休息室，將此卡【橫置】〕你選擇自己休息室的卡片1張，回到牌組，將那個牌組洗牌。
```

可以看到幾個定調：直譯不改寫語序、`パワー→攻擊力`、`控え室→休息室`、`山札→牌組`、成本框用 `〔 〕`、【橫置】保留方括號。這就是 §3.3 第二層要對齊的目標。

**人工校對**：跑一支簡易的 CLI 或 HTML 對照表，左右並排日文/中文逐張看過。120 張大約 1~2 小時可以完成。校對過的把 `translation_status` 改為 `reviewed`。

> **為什麼要人工校對**：牌組管理器的價值在於你能信任上面的文字。一個「你可以」翻成「對手可以」的錯誤，在實際對戰時是會出事的。120 張的量，一次校對完可以用很久，投報率很高。

### 3.5 階段一產物

| 檔案 | 用途 |

| `fetch_cards.py` | 抓取官網卡表 → `raw_cards.json` |

## 4. 階段二：iOS App（SwiftUI）

### 4.1 技術選型

| 項目 | 選擇 | 理由 |
|---|---|---|
| 開發環境 | Xcode 16+（在 Mac 上開發） | iOS 開發必須用 Mac 上的 Xcode |
| 目標平台 | iOS 17.0+（iPhone 為主，iPad 相容） | SwiftData 需 iOS 17；涵蓋近年多數機型 |
| UI 框架 | SwiftUI | 已有 SwiftUI 開發經驗，可延續 |
| 卡片資料 | Bundle 內 JSON + 記憶體結構 | 唯讀、資料量小、不需要資料庫 |
| 牌組儲存 | SwiftData | 需要持久化與 CRUD，原生整合最省事 |
| 卡片圖片 | 線上下載 + 本機磁碟快取 | 首次瀏覽後即可離線；不隨 App 打包 |
| 網路 | 僅圖片下載，受使用者設定的網路政策約束 | 文字資料完全離線；行動數據用量由使用者決定（見 §4.4.7） |
| 第三方套件 | 無 | 需求不複雜，不引入依賴 |

> **為什麼卡片資料不放 SwiftData**：卡片是唯讀靜態資料，120 筆全部載入記憶體不到 1 MB，用 Swift 的 `filter` 搜尋速度綽綽有餘。放進 SwiftData 反而要處理首次匯入、版本遷移等問題，複雜度不划算。

#### 4.1.1 iOS 特有的前置條件

這幾點在 macOS 上不存在，開工前要先確認：

| 行動網路 | 首次下載卡圖若用 4G/5G 會消耗流量。提供三段式網路政策設定，預設「僅 Wi-Fi」（見 §4.4.7） |

### 4.2 資料層設計

```swift
// ── 唯讀卡片資料（來自 JSON）─────────────────

/// 邏輯上的「一張卡」：同名同文字，可能有多種刷版
struct Card: Codable, Identifiable, Hashable {
    let id: String                  // 基礎卡號 "BRD/W139-075"
    let printings: [Printing]       // 所有刷版，[0] 為普卡
    let nameJP: String
    let nameZH: String
    let cardType: CardType
    let color: CardColor
    let level: Int
    let cost: Int
    let power: Int?                 // 事件/CX 為 nil
    let soul: Int?
    let trigger: TriggerIcon?
    let traitsJP: [String]
    let traitsZH: [String]
    let textJP: String
    let textZH: String
    let translationStatus: TranslationStatus
    let source: CardSource

    var defaultPrinting: Printing { printings[0] }
}

/// 同一張卡的某個刷版（稀有度不同、圖不同、文字相同）
struct Printing: Codable, Identifiable, Hashable {
    let id: String              // "BRD/W139-075" / "-075S" / "-075SSP"
    let rarity: String          // "RR" / "SR" / "SSP"
    let imageURL: URL
    let isFoil: Bool            // 是否為簽名/特殊加工版
}

enum CardType: String, Codable { case character, event, climax }
enum CardColor: String, Codable { case yellow, green, red, blue }
enum TriggerIcon: String, Codable {
    case soul, soul2, gate, treasure, comeback
    case draw, pool, shot, standby, choice
}
enum TranslationStatus: String, Codable { case machine, reviewed, manual }
enum CardSource: String, Codable { case booster, trialDeck }

// 啟動時載入一次，全 App 共用
@Observable
final class CardDatabase {
    private(set) var cards: [Card] = []
    private var cardIndex: [String: Card] = [:]        // 任一刷版卡號 → Card
    private var printingIndex: [String: Printing] = [:] // 刷版卡號 → Printing

    func load() throws { /* 讀 Bundle JSON */ }
    func card(forPrinting id: String) -> Card? { cardIndex[id] }
    func printing(id: String) -> Printing? { printingIndex[id] }
    func search(_ query: SearchQuery) -> [Card] { /* 見 §4.4.1 */ }
}


// ── 可寫牌組資料（SwiftData）─────────────────

@Model
final class Deck {
    var name: String
    var createdAt: Date
    var updatedAt: Date
    var note: String
    @Relationship(deleteRule: .cascade) var entries: [DeckEntry]
}

/// 一筆 = 某張卡的某個刷版放了幾張
/// 例：泰蕾莎 2 張 RR + 1 張 SR → 兩筆 DeckEntry
@Model
final class DeckEntry {
    var printingID: String  // 刷版卡號，如 "BRD/W139-075S"
    var count: Int
    var deck: Deck?
}
```

**關鍵設計說明**：

- `Card` 與 `Printing` 改為對稱結構——普卡不再是「本體」、平行卡不再是「附屬」，普卡就是 `printings[0]`。這樣處理刷版時不必到處寫特例分支
- **`DeckEntry` 以刷版為單位**。泰蕾莎放 2 張 RR + 1 張 SR，就是兩筆 entry。要算總張數時，依 `Card` 分組加總即可
- `DeckEntry` 仍只存字串 ID，不存卡片內容。未來翻譯修正、重新產出 JSON 替換進去，既有牌組不需要遷移就自動更新
- **⚠️ 官網卡表是否會標示「簽名卡（SP）」等特殊加工，需在 M0 一併確認**。`isFoil` 欄位先預留，抓不到就一律 `false`

**為什麼要分兩層**：3,427 張卡一次全攤開，捲到死也找不到東西，而使用者心裡的第一個問題

**搜尋不被這一層擋住**（這是設計重點）：搜尋列固定在最上面，一開始打字就直接跳過作品選單、

|---|---|
| 點作品磚 | 推進該作品，之後的搜尋與篩選都鎖在這部作品內 |
| 在最上層直接搜尋 | 作品選單就地換成跨作品結果；清空關鍵字就退回選單 |
| 「不分作品瀏覽全部卡片」 | 舊的全表瀏覽，擺在選單最下面，不搶主線 |

### 4.4 核心功能規格

#### 4.4.1 搜尋與篩選

```swift
struct SearchQuery {
    var keyword: String = ""        // 比對卡號、日文名、中文名、能力文字
    var levels: Set<Int> = []       // 空 = 不篩選
    var colors: Set<CardColor> = []
    var types: Set<CardType> = []
    var triggers: Set<TriggerIcon> = []
    var traits: Set<String> = []
    var sourceOnly: CardSource? = nil
}
```

- 關鍵字同時比對日文與中文，且**忽略大小寫、忽略卡號中的斜線**（輸入 `w139075` 也能找到 `BRD/W139-075`）
- 多個篩選條件之間是 AND，同一篩選內的多選是 OR
- 搜尋結果即時更新（120 筆資料，不需要 debounce）
- 預設排序：等級 → 顏色 → 卡號

#### 4.4.2 牌組編輯與刷版指定

**基本操作（快速路徑）**

- 搜尋結果每張卡有 `＋` / `－` 按鈕，直接調整張數
- 按 `＋` 時**預設加入普卡刷版**（`printings[0]`），不打斷操作節奏
- 縮圖徽章顯示該卡在牌組中的**總張數**（跨刷版加總）
- 刪除到 0 張時自動移除該 `DeckEntry`

**刷版指定（進階路徑）**

牌組編輯畫面中，每一列可用 `DisclosureGroup` 展開成刷版明細：

```
▾ 海灘天使 泰蕾莎              ×4
    RR   BRD/W139-075     2  ＋ －
    SR   BRD/W139-075S    1  ＋ －
    SSP  BRD/W139-075SSP  1  ＋ －
                          ─────────
                     合計  4 / 4 上限
```

- 各刷版獨立增減，合計超過 4 張時整列標紅
- **長按卡片**（`.contextMenu`）跳出「轉換刷版」選單，直接把 1 張 RR 換成 SR，省去一減一加兩次點擊
- 未展開時只顯示總張數與一排小小的稀有度標籤（如 `RR×2 SR×1 SSP×1`），不佔版面
- `＋` `－` 按鈕在 iPhone 上要留足 **44×44 pt 觸控區**，視覺上可以小，可點範圍不能小

**設計取捨**：預設走普卡、進階才展開，是為了讓「單純組牌」和「對照實體收藏」兩種使用情境不互相干擾。你組牌思路正順的時候不會被稀有度選擇打斷；等牌組定案要去收卡時，再展開逐張指定。

#### 4.4.3 規則驗證

WS Neo-Standard 建構規則：

| 規則 | 檢查方式 | 違規顯示 |
|---|---|---|
| 牌組正好 50 張 | 全部 `DeckEntry.count` 加總 | 紅色計數 `48 / 50` |
| CX 卡正好 8 張 | 篩 `cardType == .climax` 後加總 | 紅色計數 |
| **同一「卡名」最多 4 張** | 依 `nameJP` 分組加總（跨刷版） | 該組標紅 |
| 所有卡片同一作品編號 | 檢查卡號前綴 | 首版單一作品，恆為真 |

> **⚠️ 三層概念不要混淆**：
>
> | 層級 | 例子 | 與 4 張上限的關係 |
> |---|---|---|
> | 刷版（Printing） | `-075` / `-075S` / `-075SSP` | **不獨立計算**，全部併入同一張卡 |
> | 卡片（Card） | 基礎卡號 `BRD/W139-075` | 通常等同卡名，但不保證 |
> | 卡名（Name） | 「ビーチの天使 テレーゼ」 | **這才是 4 張上限的判斷依據** |
>
> 為什麼不能用 Card 分組就好？因為存在**不同基礎卡號但卡名相同**的情況——例如補充包與預組各收錄一張「蒼の魔女 シェラザード」，卡號不同、能力可能也不同，但因為同名，兩者合計仍只能放 4 張。實作 `DeckValidator` 時務必以 `nameJP` 分組。

#### 4.4.4 統計檢視

- 等級曲線（Lv0/1/2/3 各幾張）
- 顏色分布（黃/綠/紅/藍）
- 觸發圖標分布（這副 8 門牌組應該顯示：門 ×8）
- 平均費用、總魂傷
- 使用 SwiftUI 內建 `Chart`（Swift Charts）繪製

#### 4.4.6 卡圖載入與快取

這是加入圖片後最需要謹慎設計的部分。目標是：**第一次看過的卡圖，之後永遠不用再下載**。

**快取位置**：App 沙盒內的 `Library/Application Support/CardImages/`

用 Application Support 而非 Caches，因為 Caches 目錄在裝置空間不足時**會被系統清除**，我們希望這些圖長期保留。

> **⚠️ iOS 必做**：這個目錄要設 `isExcludedFromBackup = true`。否則 25~35 MB 的圖片會被算進 iCloud 備份容量，而這些圖隨時能重新下載，沒必要佔用備份空間。漏掉這一步，Apple 的審核指引也會視為問題（雖然本專案不上架，但這是好習慣）。

**檔名規則**：卡號中的 `/` 無法用於檔名，統一轉換
`BRD/W139-075` → `BRD_W139-075.png`

**載入流程**：

```
需要顯示某張卡圖
    ↓
記憶體快取（NSCache）有嗎？ ── 有 ─→ 直接顯示
    ↓ 沒有
磁碟快取有檔案嗎？ ── 有 ─→ 讀檔 → 存入記憶體快取 → 顯示
    ↓ 沒有
下載 → 寫入磁碟 → 存入記憶體快取 → 顯示
    ↓ 失敗
顯示佔位圖（卡片外框 + 卡名文字），並可點擊重試
```

**元件設計**：

```swift
actor ImageCache {
    static let shared = ImageCache()

    private let memory = NSCache<NSString, UIImage>()
    private let directory: URL          // Application Support（已排除備份）

    func forceLoad(_ printing: Printing) async -> UIImage?

    func clearCache() throws

```

**必要的細節**：

| 項目 | 做法 |
|---|---|
| 併發控制 | 網格捲動時可能同時觸發數十個下載，用 `TaskGroup` 限制同時最多 4~6 個連線 |
| 重複請求 | 同一張圖被多個 View 同時請求時，只發一次下載（用 in-flight task 字典去重） |
| 捲動取消 | 卡片捲出畫面時用 `.task` modifier 自動取消未完成的下載 |
| **記憶體上限** | `NSCache.totalCostLimit` 設 **30~50 MB**（iOS 記憶體比 macOS 吃緊得多，設太大會被系統強制終止） |
| **記憶體警告** | 監聽 `UIApplication.didReceiveMemoryWarningNotification`，收到就清空記憶體快取（磁碟的保留） |
| **降採樣** | 用 `CGImageSourceCreateThumbnailAtIndex` 依顯示尺寸解碼，**不要**把全尺寸圖直接塞進網格。這是 iOS 上圖片網格最常見的記憶體地雷 |
| **省電模式** | 開啟低耗電模式時停止背景預載，只載當前可見的圖 |

**設定頁應提供**：
- 「預先下載卡圖」按鈕（附進度條），可選**僅普卡**（約 120 張、10 MB）或**含全部刷版**（約 250 張、25~35 MB）
- **網路使用政策**（詳見 §4.4.7）
- 目前快取容量顯示
- 「清除圖片快取」按鈕

**離線行為**：文字資料完全不受影響。未快取的卡圖顯示佔位圖，且明確提示「需要連線才能載入此卡圖」，而不是無聲失敗。這在牌店現場網路不好時特別重要——建議出門前先在家用 Wi-Fi 按一次預先下載。

#### 4.4.7 網路使用政策（行動數據控制）

卡圖是本 App 唯一會用到網路的地方。台灣雖然吃到飽普及，但仍有月租量計費、國外漫遊、開熱點分享等情境，因此**是否使用行動數據交由使用者決定**，而不是由 App 擅自判斷。

**設定選項（三選一）**

| 選項 | 行為 | 適用情境 |
|---|---|---|
| **一律允許** | Wi-Fi 與行動數據都直接下載 | 吃到飽、不在意流量 |
| **僅 Wi-Fi**（**預設**） | 行動網路下不自動下載，顯示佔位圖 | 有流量限制、出國漫遊 |
| **僅 Wi-Fi，但可單張載入** | 同上，但**點一下佔位圖即可只載這一張** | 想省流量，又要偶爾查某張卡 |

預設選「僅 Wi-Fi」是保守起見——多花一次設定的力氣，好過使用者某天發現流量被吃掉。

**「單張例外」的設計理由**

這是三個選項裡最實用的一個。實際場景是你人在牌店，用行動網路，只想確認某一張卡的圖，卻不希望捲動整個圖鑑時默默下載幾十張。點擊佔位圖 → 只下載那一張 → 下載後永久快取。流量花在刀口上。

**批次預載的額外保護**

「預先下載卡圖」是唯一會一次抓幾十 MB 的操作，因此**不論上述設定為何，在行動網路下按這個按鈕都要跳確認對話框**，明確顯示預估容量：

```
目前使用行動網路
預先下載將消耗約 28 MB 流量

[取消]  [僅用 Wi-Fi 時下載]  [仍要下載]
```

選「僅用 Wi-Fi 時下載」會把任務排入佇列，等下次連上 Wi-Fi 自動繼續。

**技術實作**

```swift
@Observable
final class NetworkPolicy {
    enum Mode: String, CaseIterable, Codable {
        case always          // 一律允許
        case wifiOnly        // 僅 Wi-Fi
        case wifiOnlyManual  // 僅 Wi-Fi，但可單張載入
    }

    @AppStorage("networkMode") var mode: Mode = .wifiOnly

    private let monitor = NWPathMonitor()
    private(set) var isOnWiFi = true
    private(set) var isExpensive = false     // 行動網路或個人熱點
    private(set) var isConstrained = false   // 系統「低數據模式」

    /// 自動下載是否被允許（捲動圖鑑時呼叫）
    var allowsAutomaticDownload: Bool {
        if isConstrained { return false }        // 尊重系統低數據模式
        if !isExpensive { return true }          // Wi-Fi 一律放行
        return mode == .always
    }

    /// 使用者主動點擊佔位圖時是否放行
    var allowsManualDownload: Bool {
        mode != .wifiOnly || !isExpensive
    }
}
```

**幾個容易漏掉的細節**：

| 項目 | 說明 |
|---|---|
| **用 `isExpensive` 而非只看介面類型** | 個人熱點、部分計費 Wi-Fi 也會標記為 expensive，一併擋掉才符合使用者預期 |
| **尊重系統的「低數據模式」** | `path.isConstrained` 為 true 時，不論 App 設定為何都停止自動下載。這是使用者在系統層級表態過的意願 |
| **狀態切換要即時反應** | 從 Wi-Fi 切到 4G 時，已在進行的批次預載應自動暫停；切回 Wi-Fi 再自動續傳 |
| **不要用 `allowsCellularAccess = false`** | 這是 URLSession 層級的硬性設定，切換模式時得重建 session。改為在發出請求前檢查 `NetworkPolicy` 較有彈性 |
| **iOS 系統設定也有一層** | 使用者可在「設定 → 行動服務」關閉本 App 的行動數據權限。此時請求會失敗，錯誤訊息要能區分「你關掉了行動數據」與「網路連不上」 |

**選配：流量統計**

在設定頁顯示「本月經由行動網路下載：X MB」。實作只需在每次下載成功時累加位元組數，並記錄月份。這不是必要功能，但能讓使用者對「到底花了多少流量」有實感，也方便判斷要不要改設定。

**離線與受限時的畫面表現**

佔位圖要能區分三種狀態，不要都畫成一樣：

| 狀態 | 顯示 |
|---|---|
| 載入中 | 骨架動畫（shimmer） |
| 因政策未下載 | 卡片外框 + 卡名 + 小小的「省流量」圖示，可點擊載入 |
| 下載失敗 | 卡片外框 + 卡名 + 重試圖示 |

#### 4.4.8 卡片資料線上更新

**目的**：之後出新彈、或發現翻譯有錯字，能改一次線上資料就讓 App 自己更新，**不必回 Xcode 重新打包安裝**。這是整個資料/程式分離架構最實際的回報。

> **範圍界定（重要）**：這裡更新的是**卡片資料（`brd_cards.json`）**，不是 App 程式本身。iOS 禁止 App 下載並執行新程式碼，所以介面、功能的變更仍須回 Xcode——但那些目前已定案、不在計劃內。本節只做資料更新。

**為什麼這在現有架構下幾乎免費**：`DeckEntry` 只存卡號、不存卡片內容（見 §4.2）。因此替換整份卡表後，既有牌組會自動套用新資料，不需要任何遷移。這是一開始就埋好的設計，現在收成。

**運作方式**

```
線上放 manifest.json + 各作品的卡表（任何靜態空間都行）

App 啟動時（或按「檢查更新」）：
  下載 manifest.json（幾百 bytes）
      ↓
  逐部作品比對：線上 data_version > 本地？
      ├─ 全部都否 → 顯示「已是最新版本」
      └─ 有幾部是 → 列出「孤獨搖滾！ v1 → v2」讓使用者決定
                ↓ 使用者點「更新」
              只下載有變動的那幾份
                ↓
              解得開？作品代號對得上？不是空的？
                ↓
              寫暫存檔 → replaceItemAt 原子性替換
                ↓
              CardDatabase.reload()，畫面即時反映
```

**版本號的顆粒度：每部作品各一個**

計劃書 v1.6 原本假設單一 `brd_cards.json`，一個全域 `data_version`。實際上收錄了 10 部作品共
3,427 張卡，全量替換每次都要重抓約 2~3 MB，但維護新彈時通常只動其中一份。因此改成
**每部作品各自帶 `data_version`**，寫在該作品 JSON 的 `meta` 裡，App 逐部比對、只抓有變動的。

本地版本直接讀「已載入的卡表」的 `meta.data_version`，**不另外記一份版本表**——兩邊分開記，
遲早會對不上（下載成功但沒寫進版本表、或反過來）。已經載進來的就是事實。

**`manifest.json` 結構**

```json
{
  "schema_version": 1,
  "updated_at": "2026-09-01T00:00:00+08:00",
  "notes": "新增 BD/W54 第二波簽卡；修正泰蕾莎能力錯字",
  "sets": [
    { "title_code": "BD/W54", "file": "bdgbp_cards.json",
      "data_version": 3, "url": "bdgbp_cards.json" },
    { "title_code": "HOL", "file": "hol_cards.json",
      "data_version": 1, "url": "hol_cards.json" }
  ]
}
```

- `file` 是要寫成的本機檔名，**必須對得上 Bundle 內的檔名**，不然蓋不掉內建版
- `url` 可以是絕對網址，也可以相對於 manifest 的位置（`URL(string:relativeTo:)`）
- `schema_version` 若比 App 支援的新，提示「請回 Xcode 更新 App 本身」而非硬讀，避免舊程式讀不懂新格式而崩潰
- `notes` 顯示給使用者看，讓你知道這次更新了什麼
- 本地沒有的 `title_code` 也算更新——**新彈就是這樣進來的**

manifest 由 `tools/make_manifest.py` 從 Resources/ 直接產生，不必手寫版本號。

**本地儲存策略**

App 內建 10 份卡表（打包時的初始版本），下載的新版存到
`Library/Application Support/CardData/`。**同檔名時下載版蓋過內建版**，
這樣從沒更新過也能離線運作，更新過就用新的。

用 Application Support 而非 Caches：Caches 在裝置空間不足時會被系統清掉，
卡表被清掉就悄悄退回內建的舊版了。卡圖那邊反過來——隨時能重抓，所以排除備份。

設定頁另外提供**「還原為 App 內建卡表」**，把下載的檔案全部刪掉。線上卡表出問題時
（譯錯、傳錯檔）要有一條退路，不然只能重裝 App。

**元件設計**

```swift
@Observable @MainActor
final class DataUpdater {
    enum State: Equatable {
        case idle
        case checking
        case updateAvailable([Pending])      // 哪幾部作品要更新
        case downloading(done: Int, total: Int)
        case upToDate
        case failed(String)
    }

    struct Pending: Identifiable {
        let titleCode, titleName, file: String
        let url: URL
        let fromVersion, toVersion: Int      // fromVersion == 0 表示新作品
    }

    /// 卡表來源網址由使用者自己填（見下方「為什麼不寫死網址」）
    var manifestURLString: String

    func checkSilently(against: CardDatabase) async   // 啟動時
    func check(against: CardDatabase, silent: Bool) async
    func performUpdate(_ pending: [Pending], database: CardDatabase) async
    func revertToBundled(database: CardDatabase) async
}
```

**為什麼不寫死網址**

§6.3 訂的是「不公開發布、不分發打包後的資料檔」。把 10 份卡表推上 public repo
跟這條有牴觸，而這是**你的**取捨、不是程式該替你決定的。所以 App 不預設任何網址，
留一格讓你自己填；**空著就等於這個功能關閉**，一律使用內建卡表。

**幾個穩健性細節**

| 項目 | 做法 |
|---|---|
| 原子性替換 | 下載到暫存檔 → `JSONDecoder` 驗證解得開 → `replaceItemAt` 一次換掉。中途失敗不影響現有資料 |
| 三道落地前檢查 | 解得開、`title_code` 對得上、卡片陣列非空。少了中間那道，傳錯檔就會把 A 作品蓋成 B 作品 |
| 部分失敗 | 多部作品逐一安裝，中途失敗時**已裝好的留著**並 reload，錯誤訊息指明停在哪一部 |
| 啟動不阻塞 | 卡表載完、畫面已經能用了才在背景查一次，**絕不擋開場畫面** |
| 更新頻率 | 一天查一次就夠；上次檢查時間存進 UserDefaults，跨重開 App 仍有效 |
| 完全離線可用 | 靜默檢查失敗就當作沒事發生（`state` 回到 `.idle`），不跳錯誤打擾 |
| 不吃到快取 | manifest 與卡表都用 `reloadIgnoringLocalCacheData`。改了版本號卻讀到快取的舊 manifest，會查不到更新 |
| 尊重網路政策 | 靜默檢查看 `allowsAutomaticDownload`；使用者手動按的檢查與更新一律放行——他已經表態了 |
| 圖片快取免處理 | 卡圖本來就按卡號動態下載，新卡第一次看到時自動抓，不需要跟著資料更新一起搬 |

**設定頁呈現**

- 逐部作品列出目前版本（`孤獨搖滾！ v1`）
- 「卡表來源」：填 manifest 網址，留空即關閉
- 「檢查更新」；查到更新時就地列出 `v1 → v2`，按鈕變成「更新 N 部作品的卡表」
- `notes`、上次檢查時間
- 有下載過資料時才出現「還原為 App 內建卡表」

**你維護新彈的流程**（未來實際操作）

以賽馬娘（`uma`）為例，在 `tools/` 底下執行：

```bash
# 1. 重新抓官網卡表（出新彈才需要；只改譯文可跳過）
python3 fetch_cards.py --sets "UMA/" \
    --title-jp "ウマ娘 プリティーダービー" --title-zh "賽馬娘" \
    --out sets/uma_raw.json

# 2. 重新產出卡表。translate.py 會讀 --out 既有檔案的 data_version 並 +1
python3 translate.py --raw sets/uma_raw.json --out sets/uma_cards.json

# 3. 複製進 App 資源目錄
cp sets/uma_cards.json ../WSDeckBuilder/Resources/

# 4. 產生 manifest，順便把要上傳的卡表一起放進 dist/
python3 make_manifest.py \
    --base-url https://你的空間/wsdeck/ \
    --notes "賽馬娘新增第二彈；修正應援描述" \
    --copy

# 5. 上傳 dist/ 的內容
```

完成——所有裝置下次檢查就會拿到，而且**只會下載賽馬娘那一份**。整個過程不碰 Xcode、
不碰 App Store。因為更新的是資料而非程式，iOS 完全允許。

> **`data_version` 從哪來**：`translate.py` 讀的是 `--out` 指到的**既有檔案**。所以務必固定
> 產在 `tools/sets/`（`fetch_all.sh` 就是這樣做的），版本才會一路累加。若換個路徑輸出，
> 那份檔案沒有舊版本可讀，會從 1 重新起算，App 就偵測不到更新了。

> 唯一需要回 Xcode 的情況：新增了一部**內建卡表沒有的作品**，而你希望它也隨 App 打包。
> 純粹靠線上更新新增作品是可行的（`fromVersion == 0` 就是這個情境），只是重裝 App 後
> 會退回內建的那幾部，要再更新一次。

#### 4.4.9 牌組圖片匯出與掃圖匯入

**動機**：純文字牌表貼到 LINE 群組沒人想看，一張圖才會有人點開；但圖看完就只是圖，
對方想照著組還得手動一張張輸入。**把資料藏進圖裡**兩邊就都成立了——好看的一張圖，
同時也是可以直接掃回來的載體。

**圖的版面**

```
┌──────────────────────────────────────────────┐
│ 8門 棕色塵埃                          50 張   │
│ ┌───┐┌───┐┌───┐┌───┐┌───┐┌───┐┌───┐┌───┐   │
│ │卡 ││卡 ││卡 ││CX ││卡 ││卡 ││卡 ││卡 │   │
│ │×4 ││×4 ││×3 ││×4 ││×4 ││×2 ││×4 ││×1 │   │
│ └───┘└───┘└───┘└───┘└───┘└───┘└───┘└───┘   │
│  卡號  卡號  卡號  卡號  卡號  卡號  卡號  卡號 │
│                                     ┌──────┐ │
│ 用 WSDeckBuilder 掃這個 QR 就能匯入   │ QR   │ │
│                                     └──────┘ │
└──────────────────────────────────────────────┘
```

- 用 `ImageRenderer` 把 SwiftUI 版面畫成 `UIImage`（scale 2），寫成暫存 PNG 後交給分享面板
- **只畫已快取的卡圖**，出圖時不連網；沒快取的畫成佔位框加卡名
- **欄數跟著卡種數走**（4~8 欄）。固定 8 欄的話，只有幾種卡的牌組右半邊會空一大片
- **CX 轉 90° 填滿整格**。CX 是橫向卡，照原方向縮到同寬會比旁邊矮三分之一，
  看起來像出錯而不像設計；轉成橫置反而跟牌桌上的樣子一致。張數徽章不跟著轉

**QR 載荷格式**

刻意用純文字而非 JSON——QR 容量有限，而且掃出來的內容人眼可讀，出事時看得出哪裡壞掉：

```
WSD1|牌組名|BD/W54-001:4;BD/W54-002:3;…
```

- `WSD1` 是版本前綴，不符就當作不是本 App 的碼，往下交給其他解析器試
- 牌組名裡的 `|` 與換行會先換掉，免得解析時被切斷
- 以**刷版卡號**為單位，跟 `DeckEntry` 一致，掃回來連稀有度配置都會還原
- 錯誤更正等級用 **M**：容得下 50 張的長度，被裁到或反光時也還讀得回來

**掃回來**

用 `CIDetector(ofType: CIDetectorTypeQRCode)`，**不要用 Vision**——Vision 的條碼請求要建推論環境，
模擬器上會丟 `Could not create inference context`。QR 這種規則性圖形 CIDetector 就夠了，也不挑執行環境。

匯入入口在牌組列表，用 `PhotosPicker` 從照片圖庫選圖。⚠️ `PhotosPicker` **放在 `Menu` 裡不會彈出**，
要改成按鈕設旗標、`.photosPicker(isPresented:)` 掛在外層 View 上。

**⚠️ Info.plist 必做**：要宣告 `NSPhotoLibraryAddUsageDescription`，否則分享面板裡**根本不會出現
「儲存影像」**——iOS 是直接把該項目藏掉，而不是讓你按下去才失敗，很容易誤判成功能沒做。

| 元件 | 職責 |
|---|---|
| `DeckImageExporter` | 版面、QR 產生、載荷編解碼、輸出暫存 PNG |
| `DeckImageImporter` | 掃圖上的 QR，解不出本 App 載荷就退回既有的文字/JSON 解析器 |
| `ShareSheet` | `UIActivityViewController` 包裝。`ShareLink` 要在按下前就備好內容，但圖得先算完才有東西可分享 |

## 5. 開發順序與里程碑

| 里程碑 | 內容 | 預估工時 | 驗收標準 |
|---|---|---|---|
| **M0** | 驗證 ws-tcg 抓取可行性 **＋ 卡圖網址規則** | 2~3 hr | 能取回 10 張卡的完整欄位，且能成功下載對應卡圖 |
| **M1** | 完成抓取腳本 → `raw_cards.json` | 3~4 hr | 120 張卡欄位齊全，平行卡與圖片網址已正確歸戶 |
| **M2** | 術語表 + LLM 翻譯 + 自動驗證 | 4~6 hr | 產出 `brd_cards.json`，自動檢查全數通過 |
| **M3** | 人工校對 | 1~2 hr | 全部卡片 `translation_status` 為 `reviewed` |
| **M4** | Xcode 專案建置 + JSON 載入 + 卡片清單 | 3~4 hr | 能在**模擬器**上看到 120 張卡的中文資訊 |
| **M5** | `NetworkPolicy` + `ImageCache` + 卡圖網格（含降採樣） | 6~8 hr | **實機**捲動 60fps 不卡；切到 4G 時不自動下載；斷網後已看過的圖仍能顯示 |
| **M6** | 搜尋與篩選（含 FilterSheet） | 4~5 hr | 各篩選條件單獨與組合皆正確 |
| **M7** | 牌組 CRUD（SwiftData）+ 刷版指定 | 6~7 hr | 同張卡能分別放 2 RR + 1 SR；重開 App 資料仍在 |
| **M8** | 規則驗證 + 統計 | 3~4 hr | 跨刷版合計超過 4 張能正確標紅 |
| **M9** | 匯出（ShareLink）+ 設定頁（含網路政策）+ 收尾 | 4~5 hr | 三種網路模式行為皆正確；行動網路下預載會跳確認 |
| **M10** | 卡表線上更新（`DataUpdater`） | 3~4 hr | 改線上版本號後，App 能偵測、下載、原子替換，牌組不受影響 |
| **M11** | 實機測試與調校 | 2~3 hr | 在自己手機上安裝，實測記憶體用量、離線、行動網路與更新流程 |

**總計約 42~58 小時**。

> M10 可以排在最後，因為它跟核心功能解耦——就算之後才補上，前面的 App 也完全能用（用 Bundle 內建的初始卡表）。等你第一次要出新彈或修錯字時再做也不遲。

> **建議 M5 一做完就上實機**。圖片網格的記憶體與捲動效能是 iOS 上最容易翻車的地方，模擬器完全測不出來——它用的是 Mac 的記憶體與 CPU。愈晚發現問題，重寫的成本愈高。

**強烈建議 M0 先做**。如果官網抓取比預期困難，整個階段一的規劃需要調整（改人工輸入），這會影響時程但不影響階段二的設計。

**M1~M3 完成後可以先驗收一次**：這時 `brd_cards.json` 已經是一個獨立有價值的產物，就算 App 之後才做，這份中文卡表本身就能用。

## 6. 風險與待確認事項

### 6.1 技術風險

| 風險 | 影響 | 因應 |
|---|---|---|
| ws-tcg 卡表無法自動抓取 | 高 | 降級為人工輸入（120 張約 1~2 hr），或找其他資料源 |
| 官網欄位格式不一致（如 CX 卡無力量欄位） | 中 | 資料模型已用 Optional 處理；抓取後跑欄位完整性檢查 |
| LLM 翻譯出現數值錯誤 | 高 | §3.3 第三層的自動化數字比對是必要防線，不可省略 |
| 卡圖網址無法從卡號推導 | 中 | 改由卡表頁面解析 `<img>` 標籤，抓取時一併存入 JSON |
| 官網卡圖網址日後失效 | 中 | 首次使用即按「預先下載全部卡圖」，圖片存本機就不受影響 |
| 網格捲動時大量下載造成卡頓 | 中 | 併發上限 4~6、捲出畫面即取消（見 §4.4.6） |
| **iOS 圖片網格記憶體暴衝被系統終止** | **高** | 必須做降採樣、NSCache 上限設 30~50 MB、處理記憶體警告；M5 完成即上實機驗證 |
| **免費簽章每 7 天過期** | 中 | 開發期間用模擬器為主；長期自用可考慮付費開發者帳號 |
| 首次預載吃行動網路流量 | 低 | 預設「僅 Wi-Fi」，行動網路下批次預載另跳確認並顯示預估容量（§4.4.7） |
| SwiftData 在複雜關聯下的已知問題 | 低 | 資料模型很簡單（一對多），風險可控 |

### 6.2 待你確認的設計決策

1. **主要用哪台裝置？** iPhone 型號會影響記憶體上限的設定；若也常用 iPad，`NavigationSplitView` 分欄佈局的優先度要往前調
2. **搜尋結果預設用網格還是清單？** 網格好看好認，但同時看得到的卡片數量較少
3. **牌組列表預設要展開刷版明細嗎？** 目前設計是預設收合、只顯示總張數與小標籤
4. **匯入功能要不要做？** 首版可省略，只做匯出
5. **是否需要支援「一個牌組多個版本」？** 例如同一副牌的調整前後對照。目前設計是各建一個牌組
6. **未來擴充多作品的可能性有多高？** 若有，`brd_cards.json` 現在就該設計成可以多檔並存（其實目前 schema 已經預留 `meta.title_code`，擴充成本不高）

### 6.3 版權與使用範圍

- 卡片文字與圖片著作權屬 Bushiroad 及原作品權利方
- 本專案為個人使用工具，不上架 App Store
- 卡圖採「線上載入 + 本機快取」而非隨 App 打包，圖片來源始終是官方網址
- **卡圖快取不外流**：只存在裝置本機，不隨卡表一起發佈
- 抓取與下載維持低頻率（併發上限 4~6、請求間隔 1~2 秒），不對官方伺服器造成負擔

**v1.8 變更：卡表改為公開發佈**

原本訂的是「不公開發布、不分發打包後的資料檔」。為了讓 §4.4.8 的線上更新能運作，
卡表 JSON 改放在 public GitHub repo（GitHub raw 不支援免 token 的 private 存取）。

這件事的實際內容要講清楚，不要含糊帶過：

| 發佈的東西 | 性質 |
|---|---|
| 中文譯文 | **你自己的翻譯產出**（§3.4 明訂不搬運任何人的現成卡表） |
| 日文卡名與能力文字 | 轉載自 ws-tcg 官網，著作權屬 Bushiroad |
| 卡號、等級、費用、顏色、攻擊力 | 遊戲數值，非表達性內容 |
| 卡圖 | **不發佈**，JSON 只存官方網址 |

也就是說 public repo 裡會包含 3,427 張卡的日文原文。這是權利方的內容，公開轉載
與「個人使用」不同——這一點在原版計劃書裡被列為要避免的事，現在是明知而為的取捨。

若日後想收回，把 repo 轉為 private 即可：App 端的更新功能會開始失敗，但因為
`Application Support` 的下載版與 Bundle 內建版都還在，**既有裝置不受影響**，
只是不再收到新版。
