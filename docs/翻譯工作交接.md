# 翻譯工作交接文件

給接手翻譯的協作者（Codex）。這份文件的目標是讓你**不用問任何人**就能接手把
WSDeckBuilder 的卡表譯文補完。

分工：**你負責譯文，我（Claude）負責 App 程式與介面。** 兩邊的交界只有一個——
`tools/translations/` 底下的 JSON。你只要產出／修改那個目錄裡的檔案，
其他人跑一次產表指令就會生效，不需要動任何 Swift／Kotlin 程式碼。

---

## 1. 這個專案在做什麼

Weiß Schwarz（ヴァイスシュヴァルツ）集換式卡牌的牌組管理 App，iOS 與 Android
雙平台。卡表資料從日本官網 ws-tcg.com 抓下來，翻成**繁體中文（台灣用語）**後
供 App 使用。

目前收錄 18 部作品、5,729 張卡。

---

## 2. 最重要的三條規則

**① 一行沒把握翻完，就整行保留日文。**
絕不輸出「這張卡片が舞台に置かれた時」這種中日混雜的半成品。寧可整行日文，
使用者至少知道那是原文；混雜文會讓人以為翻錯或程式壞了。這條是整個管線的
設計前提，`translate_line()` 只要偵測到殘留假名就整行退回日文。

**② 功能性術語一律以 `tools/glossary.json` 為準。**
這是規則書用語，翻錯會讓使用者誤解卡片效果。例如：

| 日文 | 正確 | 不可用 |
|---|---|---|
| レスト | 橫置 | 休息、重置 |
| スタンド | 正置 | 站立 |
| リバース | 倒置 | 反轉 |
| 控え室 | 休息室 | 墓地、廢棄區 |
| 山札 | 牌組 | 卡組、牌堆 |
| 思い出置場 | 回憶區 | 記憶區 |

`glossary.json` 裡還有一個 `forbidden_translations`，是明確禁用的譯法，
送出前請確認沒有用到。

**③ 角色名用台灣官方譯名。**
沒有官方譯名時，用該作品中文圈通行的譯名；兩者都沒有才自己音譯。

### `names_extra.json` 的四個區塊

```jsonc
{
  "characters":     { "フリーレン": "芙莉蓮" },   // 全域角色名（176 筆）
  "name_words":     { "水着": "泳裝" },           // 全域描述詞（419 筆）
  "characters_by_set": {                          // 作品範圍的角色名
      "lrc": { "たきな": "瀧奈" }
  },
  "names":          { "<完整日文卡名>": "<完整中文卡名>" }  // 整個卡名直接對照（2260 筆）
}
```

**什麼時候放 `characters_by_set` 而不是 `characters`？**
名字短、或是常見詞的時候。例如莉可麗絲的「ミカ」放全域會咬到別的作品；
碧藍航線的「響」是艦名，但別的作品可能是普通名詞。**判斷原則：這個詞在別的
作品可能有別的意思嗎？會的話就放作品範圍。**

## 4. 翻譯管線怎麼運作

```
sets/<key>_raw.json  ──machine_translate.py──▶  translations/auto_<key>.json
                                                          │
translations/*.json （人工譯文，優先）────────────────────┤
                                                          ▼
                                              translate.py
                                                          │
                                                          ▼
                                              sets/<key>_cards.json
```

譯文優先序：**人工譯文 > 本作品機翻 > 其他作品機翻**。
所以你在 `texts_<key>_extra.json` 或 `names_extra.json.names` 寫的東西
一定會蓋過機翻結果。

### 卡名翻譯的內部順序（`translate_name()`）

理解這個順序才知道為什麼有些字典項目會互相打架：

1. 整個卡名在 `names` 裡有完全對照 → 直接回傳
2. **角色名替換（長字優先）** → 換成佔位字元，避免被後面的規則咬進去
3. 描述詞替換（`name_words` + 內建 `JP_WORDS`，單次掃描不連鎖）
4. 「の」→「的」、「たち」→「們」、去掉「ちゃん」「さん」
5. **還有假名殘留 → 整個卡名保留日文**
6. 日文新字體轉正體（`国`→`國`、`姫`→`姬`，機械式對應）
7. 還原步驟 2 的角色名

### ⚠️ 已經踩過的坑：短角色名會咬掉長詞

【我推的孩子】有個角色叫「アイ」（愛）。直接加 `"アイ": "愛"` 會把
「アイドル」（偶像）咬成「愛ドル」，假名沒清乾淨，**整張卡名反而退回日文**。

解法：因為角色名是**長字優先**，把長詞也放進同一層就會先被吃掉：

```jsonc
"osk": {
  "アイドル": "偶像",   // 先被吃掉
  "アイ": "愛"          // 輪不到它咬
}
```

同類需要注意的：「かな」（有馬かな／日文語尾）、「ミカ」、「リン」、
「レン」、「ルカ」——這些都只在作品範圍加，而且盡量用含姓氏的完整形式
（`"有馬かな": "有馬加奈"`）。

### 量測覆蓋率（我常用的檢查，建議每次改完都跑）

```bash
python3 - <<'EOF'
import json, re, glob, os
KANA = re.compile("[぀-ゟ゠-ヺー-ヿ]")
for p in sorted(glob.glob("sets/*_cards.json")):
    k = os.path.basename(p).replace("_cards.json", "")
    d = json.load(open(p)); cards = d["cards"]
    nm = sum(1 for c in cards if not KANA.search(c["name_zh"]))
    wt = [c for c in cards if c["text_jp"]]
    tx = sum(1 for c in wt if c["text_zh"] and not KANA.search(c["text_zh"]))
    print(f"{k:<7}{len(cards):>5}  卡名 {nm/len(cards):>4.0%}  能力 {tx/max(len(wt),1):>4.0%}")
EOF
```

### 找出「還差哪些詞」（決定下一步要補什麼最有效）

```bash
python3 - <<'EOF'
import json, re, sys, collections
sys.path.insert(0, ".")
import machine_translate as mt
_, names, traits, chars_base, words, by_set = mt.load_shared()
merged = dict(mt.JP_WORDS); merged.update(words)
pat = re.compile("|".join(re.escape(k) for k in sorted(merged, key=len, reverse=True)))
blocked = collections.Counter()
for key in ["pjs", "osk", "azl", "lrc", "gim"]:      # ← 改成你要查的作品
    chars = {**chars_base, **by_set.get(key, {})}
    for card in json.load(open(f"sets/{key}_raw.json"))["cards"]:
        t = card["name_jp"]
        for jp in sorted(chars, key=len, reverse=True):
            t = t.replace(jp, "")
        t = pat.sub(lambda m: merged[m.group(0)], t)
        t = re.sub(r"([^\s])の([^\s])", r"\1的\2", t)
        if mt.KANA.search(t):
            for tok in re.findall(r"[ぁ-んァ-ヴー]{2,}", t):
                blocked[tok] += 1
print(" / ".join(f"{t}({c})" for t, c in blocked.most_common(50)))
EOF
```

這段會印出「角色名都換掉之後**仍然**擋住翻譯的詞」，直接就是你該補的清單。
注意一定要在替換**之後**才統計，否則已經處理好的角色名會重複出現，誤導判斷
（我第一次就是這樣看錯的）。

## 7. 建議的推進順序

**優先做能力文字，而不是卡名。** 理由：能力文字是使用者組牌時真正需要讀懂的
內容，卡名看不懂還能靠卡圖認；而且能力文字格式固定、可複用性高——同一句
「このカードが手札から舞台に置かれた時」在幾百張卡裡重複出現，翻一次到處通。

1. **hol + uma**（1,226 行）——量最大，而且兩部都是熱門作品
2. **ovl + osk + pjs**（1,207 行）——ovl 是日版環境第一線，另兩部是新作品
3. **azl + lrc + spy + csm + gim**（982 行）
4. 收尾：bdgbp 31 張、tsk 34 張、kgl 24 張、mygo 4 張、nik 1 張
5. 最後才回頭補卡名（1,011 個）

### 兩種做法可選

**(a) 補規則引擎的字典**——改 `names_extra.json` / `glossary.json`，
跑 `machine_translate.py`。好處是一次補到位、之後新卡自動受惠；
壞處是自由發揮的日文短句（特別是 pjs 的歌名卡名）規則處理不了。

**(b) 直接寫譯文**——把譯好的內容寫進 `texts_<key>_extra.json`
（格式：`{"卡號": "中文能力文字"}`，`\n` 分行）或
`names_extra.json` 的 `names`（格式：`{"日文卡名": "中文卡名"}`）。
人工譯文優先序最高，一定會蓋過機翻。

實務上建議混用：**能力文字走 (a) 為主**（格式固定、複用率高），
**卡名走 (b) 為主**（每張都不一樣，規則沒有優勢）。

## 7.5 我實際的翻譯做法（照這個流程走）

這是我做那五部新作品時實際跑的循環，一輪大概是這樣：

### 步驟 1：先量現況

跑第 5 節的覆蓋率指令，記下數字。**每一輪結束都要再量一次**——
沒有數字就不知道自己是在前進還是在原地打轉。

### 步驟 2：找出「擋住最多卡」的東西，而不是從第一張開始翻

這是整個做法的核心。用第 5 節那段「找出還差哪些詞」的指令，
它會印出**角色名都替換完之後仍然擋住翻譯的詞**，照出現次數排序。

排在最前面的就是你該補的。補一個詞可能修好幾十張卡，
逐張翻只會修好一張。第 6.5 節那個「8 個特徵名換 30 個百分點」
就是這樣找到的。

⚠️ 這段指令一定要在**角色名替換之後**才統計。我第一次寫錯，
統計的是原始卡名，結果已經處理好的角色名一直出現在清單最上面，
看起來像沒生效，白白多繞了一圈。

### 步驟 3：分類處理

看清單上的詞是哪一類，決定放哪裡：

| 類型 | 放哪 | 例子 |
|---|---|---|
| 特徵名（`《》`裡的） | `names_extra.json` → `traits` | ホロライブ → hololive |
| 角色／艦名 | `names_extra.json` → `characters_by_set.<key>` | たきな → 瀧奈 |
| 通用描述詞 | `names_extra.json` → `name_words` | 水着 → 泳裝 |
| 整個卡名沒規則可循 | `names_extra.json` → `names` | 直接寫完整對照 |
| 能力文字整段 | `texts_<key>_extra.json` | 用卡號當 key |

**判斷放全域還是作品範圍**：這個詞在別的作品可能有別的意思嗎？
會的話就放 `characters_by_set`。短片假名（ミカ、リン、レン）一律放作品範圍。

### 步驟 4：重跑、再量一次

```bash
python3 machine_translate.py --set sets/<key>_raw.json --key <key>
python3 translate.py --raw sets/<key>_raw.json --out sets/<key>_cards.json
```

覆蓋率有上升就繼續下一輪；沒動就代表你補的詞不是真正的瓶頸，回步驟 2。

### 步驟 5：規則補不動了，才逐張手寫

當覆蓋率停在某個數字上不去，剩下的多半是自由發揮的日文短句
（pjs 的歌名卡名就是典型），規則引擎沒有辦法。這時才值得逐張寫進
`texts_<key>_extra.json` / `names_extra.json` 的 `names`。

**順序很重要**：先榨乾規則（步驟 2–4），再手寫。反過來做會白費很多力氣。

### 步驟 6：驗證與備份

```bash
python3 validate.py --cards sets/<key>_cards.json    # 未通過要是 0
./tools/backup_translations.sh                       # 每輪都做
```

## 7.6 做完之後怎麼交付（你自己推 GitHub）

你有 **`WSDeckBuilder-data` 的寫入權限**，做完一批之後由你自己發佈。
但要推的是**產出的卡表**，不是翻譯字典——這個分野很重要。

### 什麼能推、什麼不能推

| 檔案 | 推到哪 | 說明 |
|---|---|---|
| `sets/<key>_cards.json` | ✅ `WSDeckBuilder-data` 的 `cards/` | 產出的卡表，這才是要發佈的 |
| `tools/translations/**` | ❌ 不推任何 repo | 翻譯字典，見下 |
| `manifest.json` | ❌ 不要手動改 | CI 會自己重生 |

`tools/translations/` 在三個 repo 裡都被 gitignore，理由寫在 `.gitignore`：

> 日文卡名與能力文字的著作權屬 Bushiroad，中文譯文是它的衍生著作。
> 這個 repo 只放產生資料的工具，不放資料本身。

**你的字典留在本機，產物才進 repo。** 所以請照第 8 節備份 `translations/`，
那是唯一的一份，弄丟就要重做。

### 發佈步驟

```bash
# ① 先確認產表是最新的、驗證過
python3 translate.py --raw sets/hol_raw.json --out sets/hol_cards.json
python3 validate.py --cards sets/hol_cards.json        # 未通過要是 0

# ② 複製到資料 repo（第一次要先 clone）
git clone https://github.com/lungmark0618-collab/WSDeckBuilder-data.git
cp sets/hol_cards.json  WSDeckBuilder-data/cards/

# ③ 推之前一定要先 pull——CI 會自己 commit 回 manifest.json，不 pull 會被擋
cd WSDeckBuilder-data
git pull --rebase
python3 tools/check_cards.py --resources cards --manifest manifest.json   # 健檢

# ④ commit 標題會直接變成 App 裡顯示的更新說明，請寫使用者看得懂的話
git add cards/
git commit -m "補上 hololive 能力文字譯文（覆蓋率 46% → 76%）"
git push
```

推上去之後 CI 會自動跑 `make_manifest.py` 重生 `manifest.json`，
幾分鐘內手機「設定 → 檢查更新」就抓得到。

### 四個容易踩的地方

1. **推之前先 `git pull --rebase`。** CI 每次都會 commit 一個
   「Regenerate manifest」回 main，不 pull 直接 push 一定被拒。
2. **不要手改 `manifest.json`。** 那是 `cards/` 的衍生產物，CI 會覆蓋，
   手改只會製造衝突。
3. **`data_version` 不用管。** `translate.py` 每次產表自動 +1，
   App 靠這個判斷要不要重抓。
4. **`raw.githubusercontent.com` 有約 5 分鐘的 CDN 快取。**
   推完馬上按檢查更新可能還是舊的，這是正常的，不是壞掉。
   要確認有沒有生效，用不吃快取的 API：
   ```bash
   curl -s "https://api.github.com/repos/lungmark0618-collab/WSDeckBuilder-data/contents/manifest.json" \
     | python3 -c "import json,sys,base64; m=json.loads(base64.b64decode(json.load(sys.stdin)['content'])); print(len(m['sets']),'部作品 |',m.get('notes'))"
   ```

### 兩件要跟 mark 講的事

- **`tools/translations/` 由你保管之後，mark 那邊就不要再改同一份。**
  沒有合併機制，兩邊同時改只能人工對帳。
- **App 內建的卡表（iOS `Resources/`）不會因為你推 data repo 而更新。**
  那只影響「全新安裝、還沒連過網」的情況；既有使用者走線上更新一律拿得到。
  隔一陣子請 mark 把 `cards/` 同步回 `Resources/` 重新打包一次就好。

## 8. ⚠️ 一定要知道的事：譯文不在 git 裡

因著作權考量（日文卡面著作權屬 Bushiroad，中文譯文是其衍生著作），

存到 iCloud Drive 與 `~/Backups/WSDeckBuilder` 各一份（各保留最近 10 份）。

## 9. 譯文怎麼發佈到 App（發佈由你做，見 7.6；這裡講整體來龍去脈）

```
tools/sets/<key>_cards.json
   ├─▶ 複製到 WSDeckBuilder/Resources/     （iOS 內建）
   └─▶ 複製到 WSDeckBuilder-data/cards/    （線上更新）
            └─▶ push 後 CI 自動重生 manifest.json
                     └─▶ App「設定 → 檢查更新」就會抓到
```

關鍵：`translate.py` 每次產表都會把該作品的 `data_version` +1，
App 靠這個數字判斷要不要重抓。所以**只要你改了譯文並重跑產表，
使用者就會收到更新**，不需要改任何程式碼、不需要發新版 App。

資料 repo 的 commit 標題會直接變成 App 裡顯示的更新說明，
所以請寫成使用者看得懂的話（例如「補上 hololive 能力文字譯文」），
不要寫「fix typo」這種。

## 12. 常見問題（這些已經被問過，先寫在這）

**Q：專案在 Windows 上的路徑是什麼？**
沒有。專案只在 mark 的 Mac 上（`/Users/mark/Projects/WSDeckBuilder/`）。
你要嘛在那台 Mac 上做，要嘛請他把工作包傳給你（見第 3 節）。

**Q：我 clone repo 就好了吧？**
不行。`tools/translations/` 和 `tools/sets/` 都被 gitignore，
clone 只會拿到 `.py` 腳本和 `glossary.json`，沒有譯文也沒有原始卡表。
這個陷阱很陰險——clone 會成功、目錄看起來正常，直到發現沒東西可翻。

**Q：工作包裡少了 `machine_translate.py` / `translate.py` / `validate.py` / `glossary.json`？**
那是「備份包」，只裝不可再生的資料。要**完整工具包**（腳本＋術語表＋
譯文＋原始卡表＋`raw_cards.json`／`brd_cards.json`），跟 mark 要。
完整包解開後四道指令都能直接跑，已實測。

**Q：我要 push 到哪個 repo／branch／路徑？**
`lungmark0618-collab/WSDeckBuilder-data`，`main` 分支，路徑 `cards/<key>_cards.json`。
**只推產出的卡表，不要推 `tools/translations/`**（那是翻譯字典，被 gitignore，
留在你本機並自行備份）。完整步驟見第 7.6 節。
推之前記得 `git pull --rebase`——CI 會自己 commit manifest 回來。

**Q：`python3 validate.py` 報錯說缺參數？**
`--cards` 是必填：`python3 validate.py --cards sets/hol_cards.json`。
校對頁會產在 `sets/review_hol.html`，不是 `review.html`。

**Q：`--bench` 說找不到 `raw_cards.json`？**
`--bench` 需要 `tools/raw_cards.json` 和 `tools/brd_cards.json`（BRD 的
原始檔與人工譯文，當品質基準）。兩個都被 gitignore，完整工具包裡有。

**Q：`backup_translations.sh` 在 Windows 上跑不起來？**
它是 bash 腳本，而且寫死了 macOS 的 iCloud 路徑。用 WSL／Git Bash 並
自己指定目的地（`./tools/backup_translations.sh D:\backup`），
或乾脆自己壓縮 `tools/translations/`——重點是**有備份**，用什麼方式不拘。

**Q：我可以改 `machine_translate.py` 加規則嗎？**
可以，那是 git 追蹤的檔案，改了請一併說明。但**先試字典**——
多數情況補 `names_extra.json` 就夠，不需要動引擎。

**Q：`auto_<key>.json` 我可以手改嗎？**
不行，那是 `machine_translate.py` 的產物，下次重跑就被覆寫。
要覆蓋機翻結果請寫在 `texts_<key>_extra.json` 或 `names_extra.json`，
人工譯文的優先序比機翻高。

**Q：`sets/*_cards.json` 呢？**
也不行，那是 `translate.py` 的產物。改它等於改在下游，重跑就沒了。

**Q：`data_version` 要自己改嗎？**
不用，`translate.py` 每次產表會自動 +1。App 靠這個數字判斷要不要重抓。

**Q：翻譯要用簡體還是繁體？**
繁體，而且是**台灣用語**。「品質」不是「質量」、「網路」不是「網絡」、
「資料」不是「數據」。

**Q：卡片效果看不懂怎麼辦？**
`sets/<key>_raw.json` 有完整原始日文；官網 ws-tcg.com 查得到卡圖。
術語一律以 `glossary.json` 為準，不確定就看既有的 `texts_*_extra.json`
是怎麼翻的——那些是已經校對過的。
